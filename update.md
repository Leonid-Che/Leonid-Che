# update.md — журнал изменений TouchCursor

## v1.9 — пояснение к диагностике: «клиент подключается не к тому IP/порту»

### Симптом
В консоли `TouchCursorServer.exe` при переподключениях появлялось сообщение вида
«Клиент отключился … 192.168.140.66:46877», тогда как у компьютера адрес
`192.168.140.50`, а сервер слушает порт `5575`. Возникало впечатление, что
приложение «подключается к 192.168.140.66 и совсем другим портам».

### Причина (это НЕ ошибка подключения)
В логе после слова «Клиент отключился» печатается **адрес клиента из функции
accept()**, то есть IP **смартфона** (`192.168.140.66`) и его **временный
эфемерный порт** (`46877`). Сервер всегда слушает на своём IP
(`192.168.140.50`) и порту `--port` (по умолчанию `5575`). При каждом новом
TCP-соединении телефон получает новый эфемерный порт — поэтому цифры после
двоеточия меняются; это нормальное поведение TCP, а не симптом неисправности.

### Что изменено (только диагностика, протокол не затронут)
* **server.py**: строки журнала «Клиент подключился» и «Клиент отключился»
  переписаны явно: теперь в них подписано `[телефон <IP:порт>]` и добавлено
  примечание, что адрес до двоеточия — смартфона, а сервер слушает на своём
  IP:`listen_port`; в `ClientHandler` передан параметр `listen_port`.
* Проверка смоук-тестом: сессия hello→move→click живёт штатно, лог читается
  однозначно, причина обрыва (`клиент закрыл соединение (EOF)`) выводится с
  количеством команд и последней командой.

### Итог
Если после обновления APK (v1.7/v1.8 — защита от дубликата TCP-канала)
сообщения «Клиент отключился» больше не появляются при касаниях — всё в
порядке. Если появляются — смотрите поле «причина» и «сессия: N с»: короткие
сессии по нескольку секунд при каждой активации означают остаточный дубликат
клиента (пересоберите APK из этого архива), длинные сессии с причиной
`connection reset/timeout` — сетевой путь/роутер (AP-изоляция, энергосбережение
Wi-Fi телефона).

## v1.7 — корневое устранение обрыва Wi-Fi («клиент закрыл соединение (EOF)»)

### Симптом
При подключении по Wi-Fi приложение соединялось с компьютером, но после включения
управления и нажатия экранных кнопок или движения пальцем в консоли
`TouchCursorServer.exe` появлялось сообщение «Клиент отключился … команд: 1,
последняя 'hello', причина: клиент закрыл соединение (EOF)», затем клиент
автоматически переподключался. Правки v1.2–v1.5 симптом не устранили.

### Корневая причина
Диагностика v1.5 показала: сервер видел **два** TCP-соединения от телефона.
Первое (штатное, от фонового сервиса `ControlService`) работало нормально.
Второе открывалось ровно в момент нажатия кнопки «Управление: ВКЛ» — активность
`MainActivity` вызывала `startControlling()` повторно, даже когда живой канал уже
существовал. Новый (второй) экземпляр `PcClient` при публикации своего канала
закрывал чужой/предыдущий сокет — старый поток-читатель получал EOF и завершался,
а сервер фиксировал «клиент закрыл соединение». Далее шло штатное переподключение,
и цикл повторялся при каждой активации.

Дополнительный фактор: на Android таймаут, переданный в `Socket.connect(addr,
timeout)`, без предварительного `bind()` игнорируется ядром — зависшее соединение
не отпускалось вовремя и порождало «сиротские» экземпляры клиента.

### Что исправлено
* **TcpTransport.java**: перед `connect()` выполняется `s.bind(new
  InetSocketAddress(0))` — только так таймаут подключения (4 с) начинает реально
  работать на Android/Linux; ошибка bind() не критична — попытка соединения
  продолжается без него.
* **PcClient.java**:
  - добавлен метод `sameParams(mode, host, port, btMac, deviceName)` — сравнение
    параметров текущего и запрашиваемого подключения;
  - `startControlling()` стал идемпотентным: повторный вызов с теми же параметрами
    НЕ разрывает живое соединение (переподключение — только при реальной смене
    канала/IP);
  - публикация/снятие активного канала атомарны под мьютексом `connLock`; поток
    закрывает только свой транспорт, никогда — чужой;
  - флаг штатной остановки (`stopControlling/shutdown`) подавляет ложные попытки
    переподключения «сиротских» потоков.
* **ControlService.java**: синхронизация вызовов управления и защита от двойного
  запуска канала; `PARTIAL_WAKE_LOCK`, чтобы телефон не засыпал во время работы.
* **server.py**: политика «последний победитель» на каждый IP телефона
  (ключ вытеснения — адрес клиента, а не IP:порт), корректная обработка EOF и
  расширенная диагностика в лог («команд: N, последняя X, причина …»).

### Проверка
* Смоук-тест сервера: две параллельные TCP-сессии с одинаковым IP-клиента —
  первая корректно вытесняется, вторая продолжает работать; битые команды не
  рвут соединение;
* компиляция Java-классов против заглушек Android-API — ошибок нет;
* grep: все упоминания `connLock/sameParams/bind()` на месте.

### Действия
Обязательно пересобрать ОБЕ стороны:
1. Сервер: `build_exe.bat` → новый `TouchCursorServer.exe` (старый EXE не содержит
   правок протокола).
2. Клиент: забрать файлы/`git pull`, Android Studio → Sync → Clean Project →
   Assemble Project, установить новый APK.
После этого подключение по Wi-Fi остаётся стабильным при включении управления,
нажатиях кнопок и движении пальцем по тачпаду.


## v1.6 — исправлены ошибки компиляции APK в MainActivity.java (cannot find symbol)

### Симптом
При сборке APK компилятор выдавал ошибки «cannot find symbol» в
`MainActivity.java` (строка 494 и связанные):
```
error: cannot find symbol
        for (Button b : new Button[]{btnLeftClick, btnLeftDblClick, btnRightClick})
  symbol:   variable btnLeftClick
```

### Причина
В проект попала смесь двух поколений подсветки: метод `applyMouseButtonBackgrounds()`
обращался к полям `btnLeftClick / btnLeftDblClick / btnRightClick`, которые **никогда
не объявлялись и не инициализировались** — в классе по-прежнему существовали только
старые поля отдельных индикаторов `indLmb / indRmb`. Кроме того, `flashLmb()/lightRmb()`
красили именно эти отдельные TextView-индикаторы, а не кнопки мыши, что противоречило
требованию «отдельную подсветку убрать, красить сами кнопки».

### Что исправлено
* **MainActivity.java**:
  - объявлены поля `private Button btnLeftClick, btnLeftDblClick, btnRightClick;`
    вместо удалённых `indLmb/indRmb`;
  - в `onCreate()` они связываются с кнопками раскладки через
    `findViewById(R.id.btn_left_click / btn_left_dblclick / btn_right_click)` и
    вызывается `applyMouseButtonBackgrounds()` (раньше этот метод нигде не вызывался);
  - `flashLmb()`, новый `flashLmbDouble()`, `lightRmb()`, `flashRmbOnce()` теперь
    подсвечивают **сами экранные кнопки** через `setPressed()` — точно так же, как при
    нажатии пальцем (фон-selector `mouse_button_bg.xml`: обычный серый → зелёный);
  - двойной клик Громкость+ подсвечивает кнопку «ЛКМ×2» (раньше ошибочно мигала «ЛКМ»);
  - при выключении управления гасятся подсветки всех трёх кнопок.
* **Раскладки** (`layout`, `layout-port`, `layout-land/activity_main.xml`): удалены
  лишние TextView-индикаторы `ind_lmb`/`ind_rmb`, ряд кнопок приведён к пяти элементам
  (`weightSum="5"`) — ЛКМ, ЛКМ×2, ПКМ, ▲, ▼ одной высоты.
* **Ресурсы**: удалён более никем не используемый `drawable/indicator_bg.xml`; из
  `colors.xml` убраны алиасы `indicator_base/indicator_lit`, из `strings.xml` — строки
  `ind_lmb/ind_rmb` (сборка больше не зависит от этих ресурсов).

### Проверка
* `grep` по проекту: ни одного упоминания `ind_lmb/ind_rmb/indicator_*` в Java/XML не осталось;
* все XML (3 раскладки, colors, strings, mouse_button_bg) валидны;
* контрольный прогон javac: ошибок «cannot find symbol» в MainActivity.java нет.

### Действия
Заберите обновлённые файлы (или `git pull`), затем Android Studio:
**File → Sync Project with Gradle Files → Build → Clean Project → Assemble Project**.

## v1.5 — устранение ложного «Клиент отключился» по диагностике из консоли сервера

### Симптом
При подключении по Wi-Fi приложение соединялось с компьютером, но после включения
управления и нажатия экранных кнопок или движения пальцем по тачпаду в консоли
`TouchCursorServer.exe` появлялось сообщение «Клиент отключился» с указанием
IP-адреса компьютера, команд: 1, последняя 'hello', причина: клиент закрыл
соединение (EOF). Затем клиент автоматически переподключался. Правки v1.2–v1.4
симптом не устранили; именно подробный лог v1.4 («команд: 1, последняя hello»)
показал настоящую причину.

### Что показала диагностика
Счётчик команд равнялся **1** и последней была `hello`, при этом сессия жила
столько, сколько живёт второе («лишнее») соединение. Это означает, что рвался
НЕ рабочий канал управления, а его **дубликат**: телефон держал одновременно
два TCP-соединения с сервером. Второй экземпляр клиента открывался ровно в
момент включения управления (пересоздание активности / повторный вызов
startControlling / перезапущенный foreground-сервис), затем погибал — и его
закрытие сервер печатал как «Клиент отключился», хотя активный канал был жив.
Дополнительно выяснилось, что на не-Windows Python (и некоторых сборках)
объект socket не имеет метода `ioctl()`: вызов настройки TCP keepalive бросал
`AttributeError`, который не перехватывался блоком `except OSError`, поток
accept() падал со stacktrace, и сервер продолжал «висеть» на порту, разрывая
любые новые подключения сразу после hello.

### Исправления

**Сервер (`windows_server/touchcursor_server/server.py`):**

1. **Keepalive-настройка больше не убивает accept().** Обёртка
   `conn.ioctl(SIO_KEEPALIVE_VALS, ...)` расширена до
   `except (OSError, AttributeError)` — отсутствие ioctl трактуется как
   «keepalive недоступен», сервер работает дальше.
2. **Протокол «последний победитель» (last-writer-wins).** В `serve_tcp()`
   ведётся таблица активных клиентов по IP телефона (`active_by_peer`). Если
   с того же IP подключается новый канал, старый живой обработчик штатно
   вытесняется (`shutdown()` + запись в лог «Вытесняю старый канал от …»).
   Дубликаты клиента теперь никогда не выглядят в логе как обрыв рабочего
   соединения. Обратный вызов `on_closed` чистит таблицу при завершении сессии.
3. **Метод `ClientHandler.shutdown()`** — корректное серверное закрытие:
   сначала `shutdown(SHUT_RDWR)`, затем `close()`; используется при вытеснении
   и остановке сервера.

**Клиент Android (`ControlService.java`, `MainActivity.java`, `PcClient.java`):**

4. **Жёсткая защита от двух экземпляров `PcClient`.** Перед запуском нового
   клиента сервис всегда гасит предыдущий (`stale.shutdown()` + `join(1000)`),
   даже если параметры совпадают. Идемпотентный `startControlling()` дополнен
   проверками «поток мёртв» / «клиент не соединён и не запущен» — в этих
   случаях выполняется осознанный перезапуск одного клиента, а не тихий
   запуск второго.
5. **Корректная остановка потока.** Новый `PcClient.setThread(...)` хранит ссылку
   на поток клиента, чтобы `shutdown()` мог прервать зависший блокирующий
   read/connect вместо оставления «зомби-канала» открытым на стороне сервера.
6. **Убраны источники лишних переподключений в UI:** `onUnbind` сервиса при
   последнем откреплении (поворот экрана/уход активности) аккуратно выключает
   управление с корректным shutdown клиента; в `MainActivity` повторные
   вызовы startControlling при восстановлении состояния проходят по идемпотентной
   ветке без разрыва живого канала.

### Проверки
* Смоук-тест сервера (Linux, мок WinAPI): два последовательных подключения с
  одного адреса — первое вытесняется с записью в лог, второй канал исполняет
  команды; всплеск move-событий и кликов — сессия жива; `hello` отвечает
  разрешением экрана; битый JSON даёт err-ответ без разрыва.
* Компиляция изменённых Java-классов (`ControlService`, `MainActivity`,
  `PcClient`) против заглушек Android-API — ошибок нет.

### Что нужно сделать пользователю
1. Забрать архив `TouchCursor-project_v1.5.zip`.
2. **Пересобрать EXE**: `build_exe.bat` — правки accept()/keepalive критичны.
3. **Пересобрать APK** (изменены `ControlService.java`, `MainActivity.java`,
   `PcClient.java`).
4. Установить оба обновления и проверить. Если строка «Клиент отключился»
   всё же появится — сравните IP/порт в ней: теперь это может быть только
   осознанное вытеснение дубликата (сопровождающееся отдельной строкой
   «Вытесняю старый канал…»), а не потеря рабочего соединения.

## v1.4 — окончательное устранение обрыва Wi-Fi-соединения (серверная причина)

### Симптом
При подключении по Wi-Fi приложение соединялось с компьютером, но после включения
управления и нажатия экранных кнопок или движения пальцем по тачпаду в консоли
`TouchCursorServer.exe` появлялось сообщение «Клиент отключился», а затем клиент
автоматически переподключался. Правки v1.2/v1.3 симптом не устранили.

### Найденная первопричина
Читательный цикл сервера (`ClientHandler.run()`) был построен на блокирующем
сокете: `select()`/`recv()` в состоянии простоя между пакетами мог вернуть
пустое значение, которое код трактовал как EOF (клиент «отключился»). При пике
трафика move-событий (ровно момент включения управления и первых касаний)
состояние канала менялось между проверкой и чтением — ложный обрыв. Клиент при
этом зависал в бесконечном блокирующем `readLine()` без таймаута и не мог
корректно завершить штатное отключение.

### Исправления

**Сервер (`windows_server/touchcursor_server/server.py`):**

1. **Неблокирующий сокет + различение «нет данных» / «peer закрылся».**
   Сокет переводится в неблокирующий режим; читаемость проверяется через
   `recv(MSG_PEEK)`: `EAGAIN/EWOULDBLOCK` = простой (соединение живо), пустой
   результат PEEK = настоящий FIN от клиента. Ложных обрывов больше нет.
   Для неблокирующих транспортов (COM/USB) сохранено прежнее блокирующее чтение.
2. **Heartbeat.** Если клиент молчит дольше 5 с, сервер шлёт `{"resp":"ping"}` —
   канал не выглядит мёртвым ни для клиента, ни для энергосбережения Wi-Fi.
3. **Подробная диагностика обрывов.** В строке «Клиент отключился» теперь
   печатаются: число обработанных команд, последняя команда, длительность
   сессии и причина (EOF/RST/локальная ошибка). Если обрыв повторится, лог
   сразу покажет, на какой команде это произошло.

**Клиент Android:**

4. **`TcpTransport.java`: таймаут чтения сокета 5 с** (`setSoTimeout(5000)`) —
   `readLine()` больше не блокируется «навечно»; штатное завершение соединения
   не зависает.
5. **`PcClient.java`: таймаут чтения считается простоем, а не ошибкой.**
   `SocketTimeoutException` перехватывается, счётчик промахов при 5 таймаутах
   подряд шлёт серверу пробную команду `ping` (доказательство жизни канала);
   `null` от `readLine()` (настоящий EOF) корректно помечается причиной
   «Соединение закрыто сервером».
6. Из правок предыдущей итерации также сохранены: `WAKE_LOCK` +
   PARTIAL_WAKE_LOCK на время активного управления (телефон не «выгружает»
   TCP-канал во сне экрана/Doze), отключение конфликтующего стандартного
   `setKeepAlive(true)` и экспоненциальная пауза переподключения 2→30 с.

### Проверки
* Смоук-тест сервера (Linux, мок WinAPI): холостой ход 2 с → heartbeat получен,
  соединение НЕ разорвано; всплеск 300 move-команд подряд + клики/скролл →
  все исполнены, «Клиент отключился» не появляется; битая строка JSON → err-ответ,
  сессия жива; явное закрытие клиентом → в логе корректная диагностика
  (`команд: 306, последняя: 'click...', сессия: 2.7 с, причина: ... EOF`).
* Компиляция изменённых Java-классов (`TcpTransport`, `PcClient`) против
  заглушек — ошибок нет.

### Что нужно сделать пользователю
1. Забрать архив `TouchCursor-project_v1.4.zip`.
2. **Пересобрать EXE**: `build_exe.bat` (Wi-Fi) — изменения на стороне Python
   критичны, старый EXE проблему не устранит.
3. **Пересобрать APK** (изменены `TcpTransport.java`, `PcClient.java`,
   `ControlService.java`, `AndroidManifest.xml`).
4. Запустить новый сервер и новое приложение. Если обрыв всё же повторится —
   пришлите строку «Клиент отключился: ... » из консоли: теперь в ней указана
   команда-виновник и точная причина.

## v1.2 — исправление обрыва Wi-Fi-соединения при включении управления и касаниях

### Симптом
При подключении по Wi-Fi приложение соединялось с компьютером, но после включения
управления и нажатия экранных кнопок или движения пальцем по тачпаду в консоли
`TouchCursorServer.exe` появлялось сообщение «Клиент отключился», а затем клиент
автоматически переподключался.

### Найденные причины и исправления

**Сервер (`windows_server/touchcursor_server/server.py`):**

1. **Падение потока-обработчика из-за непрехваченного исключения.**
   Обработка команд шла внутри `ClientHandler.run()`; любое исключение, возникшее
   ниже защищённого блока (например, при отправке ответа в уже закрытый сокет),
   убивало поток целиком — сокет закрывался в `finally()`, и сервер фиксировал
   «Клиент отключился». Разбор каждой команды вынесен в метод `_dispatch()`,
   вызываемый из `handle_line()` через дополнительный `try/except Exception`.
   Теперь одна битая/неожиданная команда не рвёт соединение.

2. **Неограниченный рост буфера при потоке данных без переводов строк.**
   Если в канале не встречался байт `\n` (битый транспорт, мусор, разрыв посреди
   строки), буфер `self.buf` рос бесконечно вплоть до `MemoryError`, который так
   же обрывал сессию. Добавлен лимит `MAX_LINE_BYTES = 64 KiB`: при переполнении
   буфер сбрасывается с предупреждением в логе, соединение остаётся живым.

3. **Чтение канала защищено общим `except Exception`** с записью причины в лог —
   раньше любые нестандартные ошибки транспорта приводили к молчаливой смерти
   потока без диагностики.

**Клиент Android (`PcClient.java`, `ControlService.java`):**

4. **Гонка двух экземпляров клиента.** При пересоздании активности (поворот
   экрана, перезапуск) старый цикл переподключения мог в своём `finally()`
   закрыть ТРАНСПОРТ, который уже был опубликован новым экземпляром, — живой
   канал рвался ровно в момент включения управления. Публикация и снятие канала
   (`transport`/`out`/`connected`) теперь выполняются атомарно под мьютексом
   `connLock`; поток закрывает только СВОЙ транспорт (`wasMine`-проверка).

5. **Запись в потерянный канал больше не закрывает транспорт «вслепую».**
   В `writeLine()` ссылка на поток копируется под мьютексом; при ошибке записи
   устаревший экземпляр канала просто игнорируется, а актуальный помечается
   мёртвым — переподключение выполняет штатный `connectLoop`.

6. **Идемпотентный `startControlling()`.** Повторный вызов с теми же параметрами
   канала (mode/ip/port/btMac/deviceName — сравнение через новый метод
   `PcClient.sameParams()`) больше НЕ разрывает живое соединение. Переподключение
   происходит только при реальном изменении параметров (смена канала Wi-Fi/USB/BT).

### Проверки
* Смоук-тест сервера на Linux с моками WinAPI: TCP-сессия из 500+ move-событий,
  кликов, down/up, скролла и ЗАВЕДОМО БИТЫХ команд (`x:"broken"`, кнопка `middle`) —
  соединение не разрывается, на ошибки приходят ответы `{"resp":"err",...}`,
  последующие валидные команды исполняются. Стрим мусора без `\n` объёмом 138 КБ
  приводит к штатному сбросу буфера, поток жив.
* Компиляция Java-классов против заглушек Android-API — новых ошибок нет.

### Что нужно сделать пользователю
1. Забрать обновлённые файлы проекта (или собрать архив `TouchCursor-project_v1.2.zip`).
2. **Пересобрать EXE-сервер**: `build_exe.bat` (Wi-Fi-вариант) — изменения только на стороне Python.
3. **Пересобрать APK** в Android Studio (изменены `PcClient.java`, `ControlService.java`).
4. Установить новое приложение и запустить новый `TouchCursorServer.exe`.
